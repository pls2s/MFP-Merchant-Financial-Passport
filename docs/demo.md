# คู่มือ Demo — MFP (Merchant Financial Passport)

เอกสารสำหรับเตรียมและนำเสนอ demo: ขั้นตอนเปิดระบบ, บทพูดทีละขั้นพร้อมตัวเลขที่ต้องเห็นบนจอ,
การทดสอบก่อนขึ้นนำเสนอ, คำถามที่น่าจะโดนถาม และวิธีแก้ปัญหาหน้างาน
เดโมบน AWS สำหรับวิชา Cloud อยู่หัวข้อ 7

**เวลา demo ประมาณ 6–7 นาที** · ร้านที่ใช้: **1** (เคสหลัก), **2** (ร้านปกติ), สำรอง **25**, **817**

| ทำ | คำสั่ง / วิธี |

## 2. เปิดระบบ (30 นาทีก่อนนำเสนอ)

เปิด terminal 2 หน้าต่างที่ root ของ repo

```bash
# หน้าต่าง 1 — backend
.venv/bin/uvicorn backend.app.main:app --port 8000

# หน้าต่าง 2 — frontend (เชื่อม backend จริง)
cd frontend && VITE_USE_MOCK=false npm run dev
```

ตรวจ:

1. http://localhost:8000/health → `{"status":"ok","merchants":1115,"as_of":"2015-07-17"}`
2. http://localhost:5173 → เห็นรายชื่อร้าน มุมขวาบนเขียน **"เชื่อมต่อ API"** (จอกว้างไม่ถึง 960px ดูได้จากปุ่ม ⓘ)
3. เปิดร้าน 1 กดปุ่ม 💬 มุมขวาล่าง แล้วถาม copilot 1 ครั้ง (อุ่นเครื่อง — ครั้งแรกอาจช้ากว่าปกติ)
4. เปิดแท็บเตรียมไว้: ร้าน 1, ร้าน 2, หน้าผลโมเดล
5. ซูมเบราว์เซอร์ 110–125% ให้คนดูอ่านตัวเลขได้ · ปิดการแจ้งเตือนของเครื่อง

**แผนสำรองถ้า backend มีปัญหา:** ปิด frontend แล้วรัน `cd frontend && VITE_USE_MOCK=true npm run dev`
→ ใช้ข้อมูล mock ได้ทันที (ร้าน 1, 2, 25, 817 ครบ) มุมขวาบนจะเขียน "โหมด mock"

## 3. บท demo

### 0:00 — เปิดเรื่อง (30 วินาที)

> "ร้านค้าขนาดเล็กหลายร้านมีรายได้สม่ำเสมอ แต่ไม่รู้ล่วงหน้าว่าวันไหนเงินสดจะไม่พอจ่ายค่าของหรือเงินเดือน
> MFP ใช้ deep learning พยากรณ์ยอดขาย 14 วันข้างหน้า แล้วเตือนวันที่เงินอาจไม่พอ พร้อมบอกว่าเกิดจากรายจ่ายอะไร"

> "ใน demo นี้ 'วันนี้' คือ 17 ก.ค. 2558 — ข้อมูลยอดขายมาจากร้าน Rossmann ส่วนรายจ่ายเป็นข้อมูลจำลอง"

### 0:30 — หน้าเลือกร้าน (30 วินาที)

- ชี้ **ร้านสาธิต** 3 ร้านด้านบน และ badge **"เงินอาจไม่พอ N ครั้ง"**
- พิมพ์ `1` ในช่องค้นหา → คลิก **ร้านตัวอย่าง #1**

> "ระบบดูแลร้านได้ 1,115 ร้านด้วยโมเดลเดียว ร้านที่มีป้ายแดงคือร้านที่ระบบคาดว่าเงินอาจไม่พอใน 14 วันข้างหน้า"

### 1:00 — Financial Passport ร้าน 1 (3 นาที) ← ส่วนหลัก

**แถบสถานะบนสุด** — ต้องเห็น: **"อีก 5 วัน (22 ก.ค. 2558) เงินสดอาจไม่พอ ขาดประมาณ 7,917"** สาเหตุหลัก ค่าสินค้า supplier (สั่งล็อตใหญ่) และป้าย **ข้อมูลจำลอง**

> "เปิดหน้ามาเจ้าของร้านรู้เลยว่าต้องระวังวันไหน เท่าไหร่ และเพราะอะไร" (กด **ดูรายละเอียด** เพื่อเลื่อนไปการ์ดเตือนได้)

**การ์ดสรุป** — ต้องเห็น:

| การ์ด | ค่า |
| --- | --- |
| ยอดขาย 28 วันล่าสุด | **104,278** |
| สัญญาณการเงิน | **58/100** + ป้าย "ทดลอง · ไม่ใช่คะแนนเครดิต" |
| เงินอาจไม่พอครั้งถัดไป | **22 ก.ค. 2558** ขาดประมาณ **7,917** · "ที่ผ่านมาเคยเงินไม่พอ 1 ครั้ง" |

**กราฟยอดขาย** (เปิดมาเป็นช่วง **3 เดือน** แบบเรียบง่าย — ย้อนหลัง 3 เดือน + พยากรณ์ 3 เดือน)
เส้นฟ้าทึบ = ยอดจริง, เส้นฟ้าประ = คาดการณ์, เส้นขาด = วันที่ร้านปิด (อาทิตย์) · ปุ่มช่วงเวลาอยู่มุมขวาของหัวการ์ด และใช้ร่วมกับกราฟยอดเงิน

อ่าน **ประโยคสรุป** เหนือกราฟก่อน: "3 เดือนข้างหน้าคาดว่าขายได้ประมาณ 110,933 ต่อเดือน ≈ ใกล้เคียงเดิม"
และบรรทัดสีแดง "ระวัง 22 ก.ค. 2558 เงินสดอาจไม่พอ ขาดประมาณ 7,917"

> "บรรทัดบนคือคำตอบที่เจ้าของร้านต้องการ — ยอดขายจะเป็นยังไง และต้องระวังวันไหน"

กดปุ่ม **วันโปรโมชัน** (ใต้หัวการ์ด) เมื่ออยากอธิบายว่ายอดขึ้นลงเพราะอะไร (แถบเขียว = โปรโมชัน) แล้วกดอีกครั้งเพื่อปิด
ปุ่มอื่นในแถวเดียวกัน: วันหยุดนักขัตฤกษ์, วันที่เงินเคยไม่พอ, ยอดขายหลังวันนี้ (จริง + จำลอง) — แต่ละปุ่มเปิด/ปิดได้อิสระ

> "เส้นฟ้าทึบคือยอดขายจริง แถบเขียวคือวันที่ร้านมีโปรโมชัน — จะเห็นว่ายอดขายขึ้นตามโปรโมชันทุกรอบ
> เส้นประสีฟ้าคือที่โมเดล LSTM+GRU พยากรณ์ 14 วันข้างหน้า แถบสีจางคือช่วงที่ยอดขายน่าจะอยู่"

> "ช่วง 3 เดือนข้างหน้า โมเดลเดิมทายต่อกันทีละ 14 วัน แถบสีฟ้ากว้างขึ้นตามระยะเพราะยิ่งไกลยิ่งไม่แน่นอน
> ส่วนที่แรเงาเทาคือหลัง 31 ก.ค. ที่ใช้ตารางโปรโมชันจำลองแบบเดียวกับปีก่อน"

ถ้าเปิดรายละเอียดอยู่ (หรือชิป **ยอดขายหลังวันนี้ (จริง + จำลอง)**) ชี้ **เส้นเทาจุดขีด** หลัง 31 ก.ค. — **ต้องพูดทุกครั้ง:**

> "ข้อมูลยอดขายจริงจบที่ 31 ก.ค. 2558 เส้นเทาจุดขีดหลังจากนั้นเป็น**ยอดขายจำลอง**จากปีก่อน ใส่ไว้ให้เห็นภาพต่อเนื่องเท่านั้น
> ไม่ใช่ข้อมูลจริง และไม่ได้ใช้วัดความแม่นยำ — ความแม่นดูจากเส้นสีส้มกับแผงด้านล่าง"

กด **"โมเดลทายร้านนี้แม่นแค่ไหน"** ใต้กราฟหลัก (ปิดอยู่เป็นค่าเริ่มต้น) แผง **"ทาย 3 เดือนแม่นแค่ไหน"** จะเปิด — ต้องเห็น: เส้นส้มซ้อนกับเส้นฟ้าตลอด 84 วัน,
ร้านนี้ **7.6%** ทุกร้าน **8.0%** และแท่งรายช่วงจาก 6.4% (วัน 1–14) ถึง 9.2% (วัน 71–84)

> "เราทดสอบโดยให้โมเดลทายต่อเนื่อง 84 วันจาก 8 พ.ค. ซึ่งเป็นวันสุดท้ายของข้อมูลเทรน แล้วเทียบกับยอดจริง — เส้นสีส้ม"

กดปุ่ม **1 ปี** → กราฟแท่งรายเดือน: แท่งฟ้าเข้ม = 12 เดือนที่ผ่านมา, แท่งฟ้าจาง = 12 เดือนข้างหน้า (ขีด = ช่วงคาดการณ์โดยประมาณ) — ชี้ ธ.ค. ที่พุ่งทั้งสองปี

> "1 ปีข้างหน้าเป็นภาพรวมตามฤดูกาล ใช้ยอดเดือนเดียวกันปีก่อนปรับตามแนวโน้ม — ไม่ใช่ผลโมเดล deep learning
> ทดสอบย้อนหลัง 12 เดือนคลาดเฉลี่ย 5.6% สำหรับร้านนี้" → กดกลับ **3 เดือน**

**พิสูจน์ว่าโมเดลทายได้จริง** — กด **4 สัปดาห์** แล้วชี้กราฟเล็ก **"ทาย 14 วันแม่นแค่ไหน"** (เส้นส้มเทียบเส้นฟ้า 24 วันที่ร้านเปิด แผงยังเปิดอยู่จากขั้นก่อน)

> "เส้นสีส้มคือสิ่งที่โมเดลทายไว้ล่วงหน้า ก่อนจะรู้ยอดขายจริงของวันนั้น — ซ้อนกับเส้นฟ้าเกือบตลอด"

ชี้แผง **"โมเดลทายร้านนี้แม่นแค่ไหน"** — ต้องเห็น: คลาดเฉลี่ย **7.2%** (ทุกร้าน 8.2%) · **17/24 วัน** คลาดไม่เกิน 10% ·
พลาดมากสุด **11 ก.ค. 2558** (+25%)

> "เราแสดงวันที่ทายพลาดมากที่สุดด้วย ไม่ได้ซ่อน"

(ไม่บังคับ) กด **ยอดขายหลังวันนี้ (จริง + จำลอง)** เพื่อเห็นยอดขายจริง 14 วันข้างหน้า (ถึง 31 ก.ค.) เทียบกับแท่งคาดการณ์ → **ปิดก่อนไปต่อ**

**กราฟยอดเงินคงเหลือ** — ชี้เส้นที่ดิ่งลงต่ำกว่า 0 วันที่ 22 ก.ค. ตรงกับแท่งรายจ่ายสูงสุด

> "ยอดเงินคำนวณจากยอดเงินวันก่อน บวกยอดขาย ลบรายจ่าย — วันที่ 22 มีค่าสินค้าล็อตใหญ่ 28,300 เงินจึงติดลบ
> ต่ำสุดประมาณ −7,917" ชี้ป้าย **ข้อมูลจำลอง**

กดช่วง **"3 เดือน"** — ชี้เส้นประสีส้มวันที่ **2 มิ.ย.**

> "นี่คือประวัติ 6 เดือน ร้านนี้เคยเงินไม่พอมาแล้วครั้งหนึ่งเมื่อ 2 มิ.ย. ขาดประมาณ 2,047 ตอนค่าสินค้าครบกำหนด
> ทุกวันที่ 25 เจ้าของร้านถอนเงินส่วนที่เกินเงินสำรองออกไป เงินจึงไม่สะสมเกินจริง"

หลัง 31 ก.ค. เส้นจะจางลงในพื้นหลังเทา "ไกลกว่า 14 วัน · แม่นน้อยลง" และมีป้ายกรอบประ "4 ส.ค. อาจขาด 6,443"

> "ช่วงนี้ใช้ยอดขายที่โมเดลทายต่อเนื่อง 3 เดือน (ช่วง 1 ปีใช้ภาพรวมรายเดือน) กับรายจ่ายจำลองรอบเดิม
> เป็นสถานการณ์คร่าว ๆ ไม่ใช่คำเตือนแน่นอน คำเตือนจริงคือการ์ด 14 วันด้านล่าง"

(ถ้าอยากโชว์ประวัติที่ชัดกว่า เปิดร้าน **25** แล้วกด **1 ปี** — เคยเงินไม่พอ 6 ครั้งตั้งแต่ ม.ค.)

**การ์ดเตือนเงินสด** (อยู่ถัดจากกราฟยอดขาย ก่อนกราฟยอดเงิน — เล่าลำดับนี้ก่อนกราฟยอดเงินก็ได้) — ต้องเห็น 2 ใบ:

- **22 ก.ค. 2558 ขาดประมาณ 7,917** — สาเหตุหลัก "ค่าสินค้า supplier (สั่งล็อตใหญ่) 28,300"
- **28 ก.ค. 2558 ขาดประมาณ 2,980**
- กดแท็บ **ที่ผ่านมา**: **"ที่ผ่านมาเงินสดเคยไม่พอ 1 ครั้ง"** → 2 มิ.ย. 2558 ขาด 2,047

> "ระบบไม่ได้บอกแค่ว่าเงินจะขาด แต่บอกวันที่ จำนวนเงิน และรายจ่ายที่เป็นสาเหตุเรียงจากมากไปน้อย
> เจ้าของร้านจะรู้ว่าควรเลื่อนการสั่งของล็อตใหญ่ หรือเตรียมเงินไว้ก่อน" ชี้ป้าย **ข้อมูลจำลอง**

ชี้กราฟ **โอกาสรายวัน** เหนือการ์ด: 22 ก.ค. มากกว่า 99%, 28 ก.ค. **88%**

> "แต่ละวันมีโอกาสเป็น % — เราให้โมเดล 10 ตัวทายซ้ำตัวละ 20 รอบโดยเปิด dropout ไว้ ได้ยอดขาย 200 แบบ
> บวกความผันผวนจริงจากช่วง Validation แล้วนับว่ากี่แบบที่เงินติดลบ ตรวจย้อนหลังแล้วแม่นกว่าเตือนแบบ ใช่/ไม่ใช่
> แต่ % ช่วงกลางยังต่ำกว่าความจริง เราเขียนข้อจำกัดไว้ใน 'หา % จากไหน'"

**สัญญาณการเงิน**

> "คะแนนนี้เป็นสัญญาณทดลอง มาจาก 5 องค์ประกอบที่เปิดให้เห็นทั้งหมด ไม่ใช่คะแนนเครดิต
> ร้านนี้ยอดขายสม่ำเสมอ แต่เงินสำรองต่ำ จึงได้ 58"

**ผู้ช่วยการเงินร้านค้า (แชต)** — กดปุ่มวงกลม 💬 มุมขวาล่าง หน้าต่างแชตจะเปิดทับมุมจอ ดูตัวเลขในหน้าต่อได้ · คุย 2 รอบ (รอรอบละ 2–4 วินาที)

1. กดปุ่ม **"ควรทำยังไงให้ผ่านวันที่เงินไม่พอ"** → ต้องเห็นวันที่ 22 ก.ค. ขาด 7,917 และทางออก "เลื่อนค่าสินค้าล็อตใหญ่ 28,300 ออกไป 7 วัน"
2. พิมพ์ถามต่อ **"แล้วถ้าเลื่อนจ่ายตามนั้น เงินต่ำสุดวันไหน"** → ต้องได้ **2,129 วันที่ 29 ก.ค. 2558** และไม่มีวันที่เงินไม่พอ

> "ผู้ช่วยใช้ Typhoon ซึ่งเป็น LLM ภาษาไทย คุยต่อเนื่องได้ และตอบคำถาม 'ถ้า...' จากสถานการณ์ที่ระบบคำนวณไว้จริง
> AI ไม่ได้คำนวณเอง — ระบบตรวจทุกตัวเลขในคำตอบ ถ้าแต่งตัวเลขหรือแนะนำให้กู้เงิน จะถูกตัดแล้วใช้คำตอบสำรองแทน"

(ไม่บังคับ) โชว์ว่ามีขอบเขต: ถาม **"ควรไปกู้เงินธนาคารไหม"** → ต้องตอบว่าไม่ให้คำแนะนำด้านสินเชื่อ แล้วสรุปสถานะเงินสดแทน

## 5. คำถามที่น่าจะโดนถาม

**ถาม: รู้ได้ยังไงว่าโมเดลทายได้จริง ไม่ได้จำข้อมูล?**
ตอบ: แบ่งข้อมูลตามเวลา ช่วง Test 42 วันสุดท้ายไม่เคยใช้เทรนหรือเลือกโมเดล เลือก config จาก Validation เท่านั้น
และ LightGBM ใช้ lag ≥ 14 วันเพื่อไม่ให้เห็นค่าในช่วงพยากรณ์ — ดูได้บนกราฟโดยกดแสดงรายละเอียด

**ถาม: ทำไมไม่ชนะ LightGBM ชัด ๆ?**
ตอบ: LightGBM เป็น baseline ที่แข็งมากสำหรับข้อมูลตาราง โมเดลเดี่ยวแต่ละ seed ทัดเทียมกับ LightGBM แต่แกว่งมากกว่า
พอเฉลี่ย 5 seed (10 โมเดล) แล้วได้ 8.17% เทียบ 8.24% ส่วนต่าง 0.07 จุด ช่วงความเชื่อมั่น 95% [−0.14, −0.01] — เล็กแต่ไม่ใช่โชค
รายละเอียดใน `docs/report_ws1.md` หัวข้อ 7.3

**ถาม: อะไรทำให้ LSTM ทำงานได้ดี?**
ตอบ: ablation พบว่าการ normalize ยอดขายต่อ window สำคัญที่สุด (ตัดออกแล้ว error เพิ่ม 3 จุด)
รองลงมาคือ store embedding (+0.86 จุด)

**ถาม: ทำไมบางทีผู้ช่วยตอบเป็น "สรุปอัตโนมัติ"?**
ตอบ: ถ้า AI ใส่ตัวเลขที่ตรวจไม่ได้ (เช่น หารยอดเป็นรายวันเอง) ระบบจะให้ลองใหม่ ถ้ายังไม่ผ่านจะตอบด้วย template
ที่ตอบตรงคำถามจากตัวเลขของระบบ — ไม่มีวันแสดงตัวเลขที่แต่งขึ้น

**ถาม: AI copilot แต่งตัวเลขเองได้ไหม?**
ตอบ: ได้ ถ้าไม่มีการป้องกัน เราจึงส่งให้ AI เฉพาะตัวเลขที่ระบบคำนวณแล้ว (รวมสถานการณ์ "ถ้า..." ที่ระบบจำลองให้)
และตรวจทุกตัวเลขในคำตอบ ถ้ามีเลขที่ไม่อยู่ในข้อมูล หรือมีคำแนะนำให้กู้ จะให้ AI ลองใหม่ 1 ครั้ง ถ้ายังผิดจะใช้คำตอบแบบ template
ข้อจำกัดที่ยอมรับ: ตัวตรวจเช็กว่าตัวเลขมีอยู่จริง แต่ไม่ได้เช็กว่าจับคู่กับวันที่ถูกหรือไม่ จึงเขียนให้ผู้ใช้ตรวจกับตัวเลขในหน้าอีกครั้ง

**ถาม: พยากรณ์ล่วงหน้าได้ไกลแค่ไหน?**
ตอบ: 3 ระดับ แต่ละระดับทดสอบย้อนหลังกับยอดขายจริงแล้ว
- 14 วัน: LSTM+GRU โมเดลหลัก (test WAPE 8.2%)
- 3 เดือน: โมเดลเดิมทายต่อกันทีละ 14 วัน (ทดสอบ 84 วัน WAPE 8.0% — 42 วันแรกทับช่วง validation จึงอาจดีเกินจริงเล็กน้อย)
- 1 ปี: ภาพรวมตามฤดูกาลรายเดือน ไม่ใช่ deep learning (ทดสอบ 12 เดือน WAPE 7.2% ซึ่งวัดรายเดือน เทียบกับรายวันตรง ๆ ไม่ได้)
หลัง 31 ก.ค. 2558 ไม่มีข้อมูลโปรโมชันจริง จึงใช้ตารางจำลองแบบเดียวกับปีก่อน และติดป้ายไว้บนกราฟ

**ถาม: คะแนนสัญญาณการเงินเชื่อถือได้แค่ไหน?**
ตอบ: เป็นสัญญาณทดลองแบบโปร่งใส ไม่มีข้อมูลว่าร้านไหนผิดนัดชำระจริง จึงวัดความแม่นยำไม่ได้ และไม่ใช้ตัดสินสินเชื่อ

**ถาม: ใช้กับร้านจริงในไทยได้ไหม?**
ตอบ: ยังไม่ได้ทดสอบ โมเดลต้องการยอดขายรายวันอย่างน้อย 56 วัน และยังไม่รองรับร้านที่ไม่อยู่ในข้อมูลเทรน
แนวทาง cold-start อยู่ใน `docs/report_ws1.md` หัวข้อ 9.2

**ถาม: ทำไมเลือกวันที่ 2015?**
ตอบ: เป็นช่วงท้ายของข้อมูล Rossmann ทำให้มียอดขายจริงให้เทียบกับค่าพยากรณ์ได้

## 7. Demo บน AWS (วิชา Cloud)

ใช้ระบบเดียวกันแต่รันบน AWS Learner Lab ที่ deploy ด้วย `infra/setup.sh` (ดู `infra/README.md`)
บทนี้เล่าเรื่อง cloud: ข้อมูลไหลผ่าน service อะไรบ้าง ไม่ได้เล่าเรื่องโมเดลซ้ำ ใช้เป็นสคริปต์อัดวิดีโอสำรองด้วย

**เวลาประมาณ 6 นาที** · service ที่โชว์: S3, Lambda ×3, API Gateway, Amplify Hosting, DynamoDB, SNS, EventBridge, CloudWatch (ไม่นับ IAM/VPC)

### 7.1 เตรียมก่อนวัน demo 1 วัน

| ทำ | คำสั่ง / วิธี |
| --- | --- |
| Deploy ครบ 4 ขั้น | ทำตามคู่มือติดตั้ง จบที่ `./infra/setup.sh 4` → `tofu apply -auto-approve` |
| ยืนยันอีเมล SNS | กดลิงก์ในอีเมล "AWS Notification - Subscription Confirmation" (ไม่กด = ไม่ได้อีเมลเตือน) |
| จด URL | `cd infra/live && tofu output` → `website_url`, `api_url`, `data_bucket` |
| ไฟล์สำหรับอัปโหลด | สร้าง `uci_daily.csv` ด้วยคำสั่งด้านล่าง (ไฟล์เต็ม 23 MB เกินลิมิต 4 MB ของหน้าอัปโหลดบน AWS) |
| ซ้อม 1 รอบ | ติ๊ก 7.4 ให้ครบ แล้วปล่อย stack ไว้ (อย่า destroy) |

```bash
# ยอดขายรายวันของ UCI Online Retail (ต้องมี data/raw/online_retail/) → 305 แถว ~6 KB
python -c "import pandas as pd; df = pd.read_excel('data/raw/online_retail/Online Retail.xlsx'); \
df.assign(date=df.InvoiceDate.dt.date, sales=df.Quantity * df.UnitPrice).groupby('date', as_index=False)['sales'].sum().round(2).to_csv('uci_daily.csv', index=False)"
```

ไฟล์นี้สรุปจากข้อมูลดิบ อย่า commit (กฎ: ไม่ commit raw data) เก็บไว้ในเครื่องที่ใช้ demo

### 7.2 เปิดระบบ (30 นาทีก่อนนำเสนอ)

1. Learner Lab → **Start Lab** (session อยู่ได้ราว 4 ชั่วโมง ของที่ deploy ไว้ยังอยู่ครบ)
2. เปิด `website_url` แล้ว refresh 2–3 ครั้งจนการ์ดขึ้นครบ (กัน cold start — EventBridge ping ทุก 5 นาทีช่วยอยู่แล้ว)
3. เปิดแท็บ Console เรียงตามลำดับที่จะโชว์:
   1. Amplify → `mfp-dashboard`
   2. S3 → `mfp-<account>-data` → โฟลเดอร์ `uploads/`
   3. DynamoDB → `mfp-main` → Explore items
   4. CloudWatch → Log groups → `/aws/lambda/mfp-upload-worker`
   5. Lambda → `mfp-alerts` → แท็บ Test (ตั้ง event `{"force": true}` ไว้)
   6. EventBridge → Rules
4. เปิดกล่องอีเมลที่ใช้สมัคร SNS ไว้อีกแท็บ
5. เปิดภาพ architecture diagram และ `infra/steps/` ใน editor

### 7.3 บท demo

#### 0:00 — ภาพรวม architecture (1 นาที)

เปิด diagram

> "ระบบเดิมเป็น React + FastAPI ที่รันในเครื่อง เราย้ายขึ้น AWS แบบ serverless ทั้งหมด
> หน้าเว็บอยู่บน Amplify Hosting, request ที่ขึ้นต้นด้วย /api ถูกส่งต่อไป API Gateway แล้วเข้า Lambda ที่รัน FastAPI ตัวเดิม
> ผลพยากรณ์และข้อมูลจำลองเก็บใน S3, ผลอัปโหลดและประวัติการแจ้งเตือนเก็บใน DynamoDB,
> EventBridge สั่งเช็กเงินสดทุกเช้าแล้วส่งอีเมลผ่าน SNS, log ทั้งหมดอยู่ใน CloudWatch
> ทุกอย่างสร้างด้วย OpenTofu 4 ขั้น"

#### 1:00 — เว็บบน Amplify (1 นาที)

เปิด `website_url` → ร้าน 1 — ต้องเห็น: 104,278 · 58/100 · 22 ก.ค. 2558 ขาด 7,917

> "นี่คือ URL ของ Amplify ไม่ใช่ localhost แล้ว ตัวเลขชุดเดียวกับที่เดโมในเครื่อง
> เพราะ Lambda โหลดไฟล์ผลพยากรณ์ชุดเดียวกันจาก S3 — Lambda ไม่ได้เทรนหรือรันโมเดล แค่อ่านผลที่คำนวณไว้"

ถ้ามีคนถาม: ชี้ Amplify → Rewrites and redirects ให้ดูกฎ `/api/<*>` และ `/health` ที่ส่งต่อไป API Gateway

#### 2:00 — อัปโหลดไฟล์ผ่าน S3 (1.5 นาที) ← ส่วนหลัก

หน้า **ลองกับร้านอื่น** → ลาก `uci_daily.csv` → ขั้นที่ 1 ตรวจคอลัมน์ → กด **ขั้นที่ 2 · ถูกต้องแล้ว ส่งเข้า S3 ให้ระบบวิเคราะห์**

ระหว่างรอ หน้าจอจะขึ้นทีละขั้น: ขอ URL อัปโหลดจาก API → อัปโหลดไฟล์เข้า S3 → รอ Lambda อ่านไฟล์และบันทึกผลลง DynamoDB

ต้องเห็น: **374 วัน** · 1 ธ.ค. 2553 – 9 ธ.ค. 2554 · ยอดขายรวม **9,749,314** · เฉลี่ยวันละ **26,068**

> "ไฟล์ไม่ได้ผ่าน API เลย API แค่ออก presigned URL ให้ เบราว์เซอร์ส่งไฟล์ตรงเข้า S3
> พอไฟล์เข้าโฟลเดอร์ uploads/ S3 ก็ปลุก Lambda ตัวที่สองขึ้นมาอ่านไฟล์ รวมเป็นยอดรายวัน แล้วเขียนผลลง DynamoDB
> หน้าเว็บถามผลจาก DynamoDB ทุก 2 วินาทีจนเสร็จ"

สลับไป Console ทีละแท็บ:

1. S3 → `uploads/` → ไฟล์ชื่อสุ่ม (`<id>.csv`) ที่เพิ่งเข้ามา
2. DynamoDB → item `upload#<id>.csv` → `status = ok`, `days = 374`
3. CloudWatch → log stream ล่าสุด → บรรทัด JSON ที่มี `"status": "ok"`

> "ข้อจำกัดที่บอกตรง ๆ: บน AWS ยังไม่รันโมเดลพยากรณ์กับไฟล์ใหม่ เพราะ TensorFlow ใหญ่เกินขนาดของ Lambda แบบ zip
> และไฟล์ต้องไม่เกิน 4 MB"

#### 3:30 — แจ้งเตือนทางอีเมล (1 นาที)

Lambda `mfp-alerts` → **Test** (event `{"force": true}`) → ผลต้องเป็น `"alerts_sent": 5`

เปิดอีเมล "MFP: cash-flow gap alert (synthetic demo data)" → ต้องเห็นบรรทัด "ร้าน 1: วันที่ 2015-07-22 เงินขาด 7,917" และข้อความว่าเป็นข้อมูลจำลอง

> "ปกติ EventBridge เรียก Lambda นี้ทุกวัน 08:00 เวลาไทย มันเช็กร้านสาธิต ถ้าเจอวันที่เงินไม่พอก็ส่งผ่าน SNS
> แต่ละช่วงเงินขาดส่งแค่ครั้งเดียว เพราะบันทึกไว้ใน DynamoDB — เดโมนี้ใส่ force เพื่อส่งซ้ำ
> รายจ่ายและยอดเงินในอีเมลเป็นข้อมูลจำลองทั้งหมด"

เปิด EventBridge → Rules: `mfp-daily-alerts` (cron 08:00) และ `mfp-api-warmup` (ทุก 5 นาที กัน cold start)

#### 4:30 — IaC และค่าใช้จ่าย (1 นาที)

เปิด `infra/steps/` ใน editor
