# โอกาสที่เงินจะไม่พอ (%) — คำนวณจากอะไร

ระบบแจ้งเตือนเดิมตอบแค่ "ใช่/ไม่ใช่" จากค่าพยากรณ์ชุดเดียว ส่วนนี้ตอบว่า **"มีโอกาสกี่ %"** โดยจำลองยอดขาย 14 วันข้างหน้าหลายแบบ
แล้วนับว่ากี่แบบที่ยอดเงินติดลบ

โค้ด: `ai/gap_detection/shortfall_risk.py` · API: `GET /api/v1/merchants/{id}/shortfall-risk` ·
ผล: `data/synthetic/shortfall_risk.json`, `data/synthetic/shortfall_calibration.json`

> รายจ่ายและยอดเงินเป็น**ข้อมูลจำลอง** % นี้จึงเป็นโอกาสของร้านจำลอง ไม่ใช่การรับประกัน และไม่ได้ใช้ตัดสินสินเชื่อ

## สูตร

```
% วันที่ t = (จำนวนแบบที่ B_t < 0) ÷ 200
B_t = ยอดเงินวันนี้ + Σ (ยอดขายของแบบนั้น − รายจ่ายจำลอง)      ← สูตรเดียวกับการแจ้งเตือนเดิม
% ใน 14 วัน = (จำนวนแบบที่ยอดเงินติดลบอย่างน้อย 1 วัน) ÷ 200
```

## ยอดขาย 200 แบบมาจากไหน

| ขั้น | ทำอะไร | ทำไม |
| --- | --- | --- |
| **1. Deep learning: Monte Carlo dropout** | โมเดลหลักทั้ง 10 ตัว (LSTM + GRU × 5 seed) ทายยอดขาย 14 วันข้างหน้า ตัวละ **20 รอบ โดยเปิด dropout ไว้ตอนทาย** แต่ละรอบปิดส่วนของเครือข่ายแบบสุ่ม 20% → 10 × 20 = **200 แบบ** | วัด**ความไม่แน่นอนของโมเดล**: จุดที่โมเดลไม่มั่นใจ คำตอบแต่ละรอบจะต่างกันมาก (และ 10 โมเดลก็เห็นไม่ตรงกัน) |
| **2. ความผันผวนรายวัน** | คูณแต่ละแบบด้วย **error จริง 14 วันติดกัน** (ยอดจริง ÷ ที่ทาย) ของ ensemble ในช่วง **Validation** สุ่มจาก 3,345 ก้อน (1,115 ร้าน × 3 จุดตั้งต้น) ตัดค่าไว้ที่ 0–3 เท่า | dropout วัดได้แค่ความไม่แน่นอนของโมเดล ไม่รวมเหตุการณ์ที่ไม่มีใครทายได้ (อากาศ คู่แข่ง ฯลฯ) ใช้ทั้งก้อน 14 วันเพื่อให้สัปดาห์ที่ขายไม่ดีมักไม่ดีต่อเนื่องเหมือนของจริง |
| **3. คำนวณยอดเงิน** | ยอดเงิน ณ วันนี้ (จากยอดขายจริง) + ยอดขายแต่ละแบบ − รายจ่ายจำลองที่ครบกำหนด | ใช้สมการเดียวกับ `gaps.py` คำเตือนกับ % จึงสอดคล้องกัน |

**สัดส่วนความไม่แน่นอน (ช่วง Test):** ความแปรปรวนของยอดขายจำลองมาจาก MC dropout + ensemble **21%** และจาก error รายวัน **79%**
แปลว่าโมเดลค่อนข้างมั่นใจในตัวเอง ความเสี่ยงส่วนใหญ่มาจากความผันผวนที่ไม่มีโมเดลไหนทายได้

## ตรวจย้อนหลัง (ช่วง Test)

ใช้เฉพาะ Validation ในการสร้าง error รายวัน และ**ไม่ได้ปรับค่าใดจากผล Test** ตรวจที่ 3 จุดตั้งต้นของ Test
(19 มิ.ย., 3 ก.ค., 17 ก.ค. 2558) ซึ่งรู้ยอดขายจริงแล้ว จึงคำนวณยอดเงินจริงได้ ไม่นับร้านสาธิต 1, 25, 817
เพราะบิลล็อตใหญ่ของร้านเหล่านี้เป็นสถานการณ์ที่ตั้งใจใส่

**ยอดขาย:** ช่วง 10–90% ของ 200 แบบครอบยอดจริง **74.1%** ของวัน (ควรเป็น 80%) กว้างเฉลี่ย 24% ของค่ากลาง
→ ช่วงยังแคบกว่าที่ควรเล็กน้อย ปัญหาเดียวกับช่วงคาดการณ์ในรายงานหัวข้อ 7.5 (Validation ถูกใช้เลือกโมเดลแล้ว error จึงดูต่ำกว่าจริง)

**เงินไม่พอรายวัน** (46,704 ร้าน-วัน, เงินไม่พอจริง 242 ครั้ง = 0.52%)

| วิธี | Brier score (ยิ่งต่ำยิ่งดี) |
| --- | --- |
| **% จากการจำลอง** | **0.00054** |
| เตือนแบบ ใช่/ไม่ใช่ จากค่าพยากรณ์ชุดเดียว | 0.00064 |
| เดาค่าเฉลี่ย 0.52% ทุกวัน | 0.00515 |

% จากการจำลองดีกว่าเตือนแบบ ใช่/ไม่ใช่ **17%** และดีกว่าเดาค่าเฉลี่ยประมาณ 10 เท่า

**Reliability: บอก % เท่านี้ แล้วเกิดจริงกี่ %**

| ช่วงที่บอก | จำนวนร้าน-วัน | บอกเฉลี่ย | เกิดจริง |
| --- | --- | --- | --- |
| 0–5% | 46,422 | 0.0% | 0.0% |
| 5–20% | 29 | 11% | 21% |
| 20–40% | 14 | 29% | 79% |
| 40–60% | 11 | 51% | 91% |
| 60–80% | 16 | 69% | 69% |
| 80–100% | 212 | 99% | 96% |

- ปลายทั้งสองข้างตรงดี: วันที่บอกเกือบ 0% ไม่เคยเกิด วันที่บอกเกือบ 100% เกิดจริง 96%
- **ช่วงกลาง (5–60%) บอกต่ำกว่าความจริง** สอดคล้องกับช่วงยอดขายที่แคบเกินไป แต่มีข้อมูลแค่ 54 ร้าน-วัน จึงยังสรุปตัวเลขแน่นอนไม่ได้
- หน้าจอจึงเขียนข้อจำกัดไว้ใต้ "หา % จากไหน" ให้ใช้ % เปรียบเทียบว่าวันไหนเสี่ยงกว่า มากกว่าอ่านเป็นตัวเลขแม่นยำ

**เงินไม่พออย่างน้อย 1 วันใน 14 วัน** (3,336 ร้าน-ช่วง, เกิดจริง 46 ครั้ง): Brier 0.0012 เทียบกับเดาค่าเฉลี่ย 0.0136

## ตัวอย่างร้านสาธิต (ณ 17 ก.ค. 2558)

| ร้าน | โอกาสใน 14 วัน | วันที่เสี่ยง |
| --- | --- | --- |
| 1 | มากกว่า 99% | 22–23 ก.ค. มากกว่า 99% · 24 ก.ค. 54% · 28 ก.ค. 88% |
| 25 | มากกว่า 99% | 22–23 ก.ค. มากกว่า 99% · 24 ก.ค. 50% |
| 817 | มากกว่า 99% | 22–23 ก.ค. และ 25–28 ก.ค. 98% ขึ้นไป · 24 ก.ค. 41% |
| 2 | ต่ำกว่า 1% | — |

22 ก.ค. ได้เกือบ 100% เพราะบิลล็อตใหญ่ที่ใส่ไว้สำหรับเดโมตั้งใจให้ขาดประมาณ 2 วันของยอดขาย ต่อให้ยอดขายดีกว่าที่ทายก็ยังไม่พอ
ส่วน 28 ก.ค. ของร้าน 1 (88%) แสดงประโยชน์ของ %: คำเตือนเดิมบอกแค่ "อาจไม่พอ" แต่ % บอกว่ายังมีโอกาส 12% ที่จะผ่านไปได้

## ข้อจำกัด

1. ช่วงยอดขายแคบกว่าที่ควร (74% แทน 80%) % ช่วงกลางจึงต่ำกว่าความจริง
2. error รายวันสุ่มจากทุกร้านรวมกัน ไม่ได้แยกว่าร้านไหนผันผวนมากหรือน้อย
3. ถือว่ารายจ่ายแน่นอน (ไม่สุ่ม) และเงินถอนของเจ้าของร้านที่เกิดในช่วงตรวจย้อนหลังเป็นรายจ่ายที่รู้ล่วงหน้า
4. จำลอง 200 แบบ ความละเอียดของ % จึงอยู่ที่ 0.5% หน้าจอแสดง "ต่ำกว่า 1%" / "มากกว่า 99%" แทน 0% / 100%
5. รายจ่ายทั้งหมดเป็นข้อมูลจำลอง

## ทำซ้ำ

python -m ai.gap_detection.build            # รายจ่ายจำลอง + คำเตือน (ต้องมีก่อน)
python -m ai.gap_detection.shortfall_risk   # ~8 นาทีบน CPU, seed 42
